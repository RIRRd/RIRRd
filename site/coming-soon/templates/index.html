How we measured +

100,000 deterministic, synthetic RPSL objects: 50,000 aut-num, 25,000 IPv4 routes, 24,997 IPv6 routes and three supporting objects. This benchmark uses no public registry data; the live test service has a separate dataset.

Both services run on this 24-CPU, 62-GiB VM, restricted to CPUs 0–15. The native Rust load client uses CPUs 16–23. IRRd has eight WHOIS and eight HTTP workers, with PostgreSQL image defaults; RIRRd has a 32-connection cap. This is not a database-tuning study. Eight concurrent clients query one implementation at a time, alternating implementation order.

WHOIS exact-key lookups and GraphQL queries for rpslPk, source and objectClass cycle across the same 50,000 AS keys. Every response is checked for framing, identity and source. Main workloads reuse connections with a three-second warmup; separate new-connection tests appear below. The client reports its own CPU use in the JSON so load-generator limits can be assessed.

Imports use three fresh databases in alternating order. File cache may be warm. Database schema migration and service startup are outside import timing. Accepted object counts match, but import validation and index coverage differ between implementations. Storage is allocated redb bytes versus the PostgreSQL cluster including WAL; container images and logs are excluded, and Redis persistence is disabled.

Idle memory is the median of three summed process PSS samples after testing: RIRRd versus the IRRd application, PostgreSQL and Redis together. Resident memory-mapped pages are included; unmapped filesystem cache is excluded. This is not peak memory.

An initial harness attempt sent an incorrect HTTP Host header and was rejected by IRRd. The client was corrected and every query profile was rerun; the rejected attempt is excluded from this comparison.

Short local synthetic tests do not cover sustained or mixed load, concurrent updates, full-size registry datasets or all supported query types.
