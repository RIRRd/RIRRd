## Occupied disk space

The fixture is the original synthetic 100,000-object PERF dataset generated by
`tools/bench/generate_fixture.py`, SHA-256
`9fe1bf623acb0499df78537f4d097582c0fd1bba0fa4c99ae4b21a38dee3a0f2`.
It contains 50,000 aut-num objects, IPv4/IPv6 routes and three support objects.
It is not a copy of a public registry. Fixtures and database files stay outside Git.

The baseline copy had already undergone ordinary `database compact --yes`,
which did not reduce its apparent length. Storage accounting showed substantial
unused room inside active B-tree leaves. Bounded, dispersed-order reinsertion
packs those leaves more densely through supported redb APIs.

| Measurement | Compacted original | Repacked copy |
| --- | ---: | ---: |
| Objects | 100,000 | 100,000 |
| Application tables | 15 | 15 |
| Stored key/value bytes | 41,996,268 | 41,996,268 |
| Allocated filesystem bytes | 102,674,432 | 79,052,800 |
| Allocated filesystem MiB | 97.92 | 75.39 |
| Apparent file MiB | 129.01 | 129.01 |

**Allocated disk space falls 23.0%, saving 22.53 MiB.** The file's logical
length stays unchanged because it retains sparse/preallocated capacity. This is
an occupied-block saving, not a claim that `ls -l` shows a shorter file.
Per-table row counts and stored bytes are identical. The complete typed logical
SHA-256 before and after is
`be81010002c8759dfb634ca872118c9002b72b0936dc99586278fc85b5525e01`.

The complete repack, including source/output index verification, independent
row hashing, compaction and closed-file reopen validation, took **34.27 s**
inside a one-CPU, 256 MiB systemd unit. Cgroup memory peak was **202.78 MiB**;
the unit exited successfully. Input cache could be warm, and cgroup memory is
not interchangeable with process RSS or whole-VM memory. This is not a
minimum-host qualification for a complete Internet dataset.

## Read performance

Both layouts used the same release binary, 16 MiB database cache, one async
worker, four blocking workers and a one-CPU/128-MiB service limit. Four validating
clients used CPUs 16–19. The server used CPU 0. Three eight-second runs per mode
and layout, with two-second warmups, alternated layout order and reused
connections. Host/file caches could be warm. No builds or fuzzers ran during timing.

| Measurement | Original | Repacked |
| --- | ---: | ---: |
| WHOIS median queries/s | 12,395 | 12,976 |
| WHOIS worst per-run p95, ms | 0.640 | 0.581 |
| WHOIS worst per-run p99, ms | 0.868 | 0.790 |
| GraphQL median queries/s | 4,266 | 4,399 |
| GraphQL worst per-run p95, ms | 1.936 | 1.932 |
| GraphQL worst per-run p99, ms | 2.674 | 2.558 |
| Median process PSS, MiB | 24.72 | 24.42 |

All **814,263** measured replies validated, with zero errors. Median throughput
rises about 4.7% for WHOIS and 3.1% for GraphQL in this fixture. These small
differences are not universal performance promises or maximum public capacity.
Public admission/rate limits are unchanged.

## Reproduce

Build the locked release and generate the original fixture outside Git. Import
it into a private offline database, then run the normal commands:

```sh
rust-irrd --config /private/original.toml database compact --yes
rust-irrd --config /private/original.toml database stats
rust-irrd --config /private/original.toml database repack --file /private/packed.redb
```

Inspect `source_file`/`output_file` bytes and the logical hash in the JSON result.
Use configurations differing only in database path to compare reads. The native
`registry_load` example validates every measured response:

```sh
target/release/examples/registry_load --endpoint 127.0.0.1:9880 \
  --mode graphql --clients 4 --keys 50000 --seconds 8 --warmup 2
```

Use unused loopback listeners, record CPU/memory limits and repeat both modes
in alternating layout order. Keep verification/export fixtures and databases
out of Git. Do not substitute unvalidated or failed runs into comparisons.
